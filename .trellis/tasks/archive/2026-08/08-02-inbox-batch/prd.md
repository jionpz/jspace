# 批量 inbox 整理【核心】

## Goal

把「整理 inbox」从逐份处理升级为**批量管线**:一次性处理 `_inbox/` 存量,分两遍(确定性零提问 / 模糊项人工过目),可中断续跑、可人工排除与纠错,且可被 M3 cron 无头驱动(只跑第一遍 + 执行日志)。这是**整个项目最高价值交付**(用户确认:批量 + 定时 + 人工调整 = 核心),filehub-scaffold 已提供正式根路径,本子任务在此之上实现批量。

## Background(确认事实)

- asset-ingest skill 已有**单文件**流程(识别→查重→归位→入脑→登记→自检),纪律:「逐份处理,MVP 每次一份资料,会话可循环调用;批量自动化留给 M2」。→ 本子任务兑现该承诺。
- skill 在 `skills/asset-ingest/`,经 `gen-assets.ts` 内嵌进工作台(改后必须重新生成)。
- filehub 正式路径已可用(`jspace filehub init` + `type: filehub` resource);未注册时批量走降级暂存区(工作台外 `../<workbench>-inbox/`)。
- 单文件逻辑已含:「失败即停」(单文件原子性)、「embedding 不可用固定提示」、查重三选(跳过/修复/升版本)。
- 父任务已定:批量两遍式 + `.processing` 幂等 + 机械校验(批量前后计数对比、确定性查重预检、召回自检贴实际输出)+ 无头只跑第一遍 + 执行日志落固定路径。

## Requirements

- **R1 批量两遍式(skill 层,asset-ingest 增 batch 模式)**:
  - **第一遍(确定性,零提问,可无头)**:扫 `_inbox/`,对每个文件判断是否"确定性"(类型/归属/命名明确、无查重冲突);确定性文件直接走单文件逻辑(识别→查重→归位→入脑→登记→自检),**零提问、单文件原子性**(该份失败即停、报告、不留半成品)。
  - **第二遍(模糊项,人工过目)**:拿不准的(归属/命名/查重冲突/类型不明)列成一张**短清单**,用户一次过目——每项可「跳过 / 改归属 / 改命名 / 升版本 / 覆盖」。
  - **汇总报告**:成功 / 跳过 / 失败 + 原因;机械校验(批量前后计数对比、确定性查重预检、召回自检贴实际 `gbrain query` 输出)。
- **R2 幂等与中断续跑**:`.processing` 标记(`_inbox/` 内点文件,doctor 已跳过点文件)标识"正在处理/已完成",中断后重跑**不重复处理**已完成项;失败项保留标记与原因,可单独重试。
- **R3 人工调整闭环**:① **处理前可排除**:用户说「这个别动」→ 加入 skip 清单,该文件本轮不处理;② **处理后纠错**:对归位/命名/分类不合适的文件,提供「撤销本次 / 重跑该份」——撤销把文件放回 `_inbox/`(或 back),重跑修复 gbrain 页与 index 登记(复用单文件「修复」语义)。
- **R4 cron 可驱动(供 M3)**:无头模式下**只跑第一遍**(确定性),模糊项留清单等用户在场时第二遍;输出**执行日志**到固定路径(路径/计数/成功/跳过/失败/每个文件结果),供下次会话检查(对接 M3 失败可见性契约)。
- **R5 CLI 只读辅助 `jspace inbox status`**:列出 `_inbox/`(或降级暂存区)文件与计数(文件名/大小/修改时间),`--json` 供无头预检;**不做**语义判断(分类/命名/查重仍由 skill/AI 完成)。空 inbox → 提示无事可做。

## Acceptance Criteria

- [ ] AC1 对含多份中文资料的 `_inbox/`,会话内「整理一下 inbox」批量整理:确定性文件零提问归位,模糊项进第二遍清单一次过目;汇总报告含成功/跳过/失败计数。
- [ ] AC2 单文件原子性:某份失败 → 该份停止并报告原因,其余文件不受影响,不留半成品页。
- [ ] AC3 中断续跑:批处理中途中断(模拟),重跑不重复处理已完成项;失败项保留标记与原因。
- [ ] AC4 人工排除:处理前指定「这个别动」→ 该文件跳过且后续可回滚;处理后对错归/错命名文件可「撤销/重跑」并修复 gbrain 页与 index。
- [ ] AC5 cron 可驱动:无头模式只跑第一遍,输出执行日志(路径/计数/成功/跳过/失败)到固定路径;模糊项留清单。
- [ ] AC6 机械校验:批量前后计数对比可查;召回自检贴出实际 `gbrain query` 输出(非静默)。
- [ ] AC7 `jspace inbox status` 列出文件/计数,`--json` 可用;空 inbox 提示无事可做;未注册 filehub 时指向降级暂存区。
- [ ] AC8 全流程回归:skill 变更后 `gen-assets` 重新生成;`init` + `doctor` 通过;现有单文件路径仍可用(未破坏)。

## Key Decisions

- **批量逻辑在 skill 层,CLI 只读**:语义判断(分类/命名/查重/召回)必须 AI,CLI 不做;`inbox status` 只服务预检与无头。专家一致保留 skill 层定位。
- **两遍式 = 人工调整的载体**:第一遍零提问(可无头),第二遍模糊清单人工过目;这直接服务用户「处理中可调整」诉求。
- **单文件原子性 + `.processing` 幂等**:失败即停该份、可中断续跑,不整批回滚。
- **执行日志落固定路径**(无头第一遍):对接 M3 失败可见性契约;具体路径见 design。
- **处理后纠错复用单文件「修复」语义**:撤销/重跑不新建机制。

## Out of Scope

- M3 cron 调度本身(本子任务只交付"可被无头驱动"的管线与日志)。
- bootstrap 引导(子任务 bootstrap-filehub)、域↔项目挂接(子任务 domain-project-link)。
- gbrain 本体修改;office 逐表抽取;重资产 embedding。
- `_inbox/` 存量的一次性历史迁移(增量收编)。

## Notes

- 依赖 filehub-scaffold 的正式根路径(已完成);skill 变更后需 `gen-assets` 重新生成。
- 无头与人工两模式共用同一套批量逻辑,差异只在「是否询问/是否写日志」。
