# JSpace 目标复审：2026 年 10 月

> 复审日期：2026-10-18（Asia/Shanghai）。
> 范围：项目定位、源码责任、官方行业证据与目标调整；不实施新 CLI、schema、模板、接线或运行服务。
> 证据分三类：仓库事实、外部官方声明、本文推论。产品发布不能证明整个行业的最终形态，源码审阅也不能替代真实环境验收。

## 结论

**JSpace 的本地、可移植、跨 harness 方向成立；旧 GOAL 对工作中心的定义偏窄，并把几项实现选择固定成了终局。**

真正应该长期保留的是：用户拥有的工作上下文、可信来源、持久成果、可迁移性和可处置的执行失败。总控文件夹、特定记忆后端与 cron 是今天实现这些价值的手段。未来入口和执行环境会变化，这些价值仍然成立。

因此本轮把目标改为“用户拥有的、可移植的个人 AI 工作底座，让同一项真实工作跨会话、跨工具持续推进”。它明确 JSpace 在完整工作中心中的责任，不把一个个人项目扩大成全能平台。跨机器接续仍受实际同步、绑定与真机验证约束。

## 从第一性原理看项目本质

用户希望把工作做完。持续工作需要目标、当前状态、资料、执行能力、产物和验收；聊天窗口只是访问它们的一种界面。

模型、harness 和客户端会换，项目往往比它们活得更久。JSpace 可以控制的持久部分包括工作规则、项目认知卡、决策、原始资料、索引与失败记录；模型的推理能力、第三方会话状态、远程系统权限与调度环境不在它控制之内。

由此得到三个约束：

1. **持久上下文必须能离开当前工具继续使用。** 不能把“同一入口”误当成“同一份可接续的工作”。
2. **工作状态不能全压进记忆。** 项目任务系统与规范文档保留执行细节，记忆帮助发现和理解它们；否则会产生多套彼此冲突的事实。
3. **执行与成果必须能分别判断。** 调起 agent 很容易，证明它交付了正确、可接手的结果需要任务自身的标准。

最小方案是在现有路由、记忆、资产和定时机制上验证交接与验收；没有证据要求新增统一工作项数据库、常驻服务或多 agent 编排器。

## 仓库事实：实现已经支持什么

以下引用是本轮审阅时的位置，未修改这些实现文件。

### 上下文与入口

- `application/context/collect.ts:21` 的 `WorkbenchState` 汇集域、pending、incident、inbox、项目卡、偏好与近期知识。它是工作台概况，没有任意业务任务的完整运行状态。
- `application/context/project-states.ts:10` 将活跃项目展示上限设为 8；`:127` 从 gbrain 的项目 state 卡中按列表与时间取摘要；`:195` 摘取“现在到哪了”。这证明项目认知注入已存在，不能证明按本次任务意图选择了全部必要上下文。
- `application/context/payload.ts:13` 将 session-start 预算设为 4 KiB；`:32` 渲染状态和按需读取路径。这是有意节制上下文的设计；进一步优化应针对实际遗漏与干扰，不是把全部历史塞进 prompt。
- `application/context/payload.ts:117` 的写回提醒与 `:139` 的 session-end 文案只提醒；`application/context/briefing.ts:88` 实现提醒去重。提醒不是持久记忆写入，也不是已完成的跨工具交接。
- `adapters/harness/capabilities.yaml:90` 起按 harness 声明 headless、MCP、事件与 lifecycle。Codex 在本项目中仍是 cron 兼容与手动会话 fallback，不能因外部 Codex 产品发展就声称本项目已完整接入。

### 定时执行与失败处置

- `application/automation/execute.ts:201` 的 `cronRun` 编译 skill 目标、选择 harness、加锁并执行；`:245` 起在 spawn 前取起跑时间，记录 duration，说明旧 GOAL 中那条时间戳缺陷已由当前源码修正，不应复活为新 backlog。
- `application/automation/execute.ts:254` 起主要用退出码、超时、是否有输出以及 inbox 批次日志变化判定状态；`:283` 对判定成功的执行关闭 incident。它没有逐业务目标的通用验收逻辑。
- `application/automation/runs.ts:35` 原子写结构化 run 记录；`application/automation/incidents.ts:69` 管理事件与证据。结构化状态是恢复与调和的机械真相，不应改成从 Markdown 自述推断。

### 持久数据与真实使用

- 资产入库具有续跑与补偿机制，但 gbrain/index 的 checkpoint 部分依赖写侧报告，不能保证跨系统原子提交。pending 保留待写正文并去重，已有不同正文时会暴露冲突，不能承诺解锁后所有写入都会落库。详见 `application/ingest/use-cases.ts:111`、`application/ingest/journal.ts:196`、`application/pending/apply.ts:51` 与 `application/pending/apply.ts:61`。
- 升级按所有权保留文件编辑与可回滚快照，投影调和有单独边界；不是对用户目录的无限制、全操作事务回滚。详见 `application/workspace/workspace.ts` 与 `application/workspace/projections.ts`。
- `skills/jspace-use/references/gbrain.md` 与全局治理将 state 定位为项目认知卡；决策、经验、状态、来源和生命周期已有纪律。应复用这些约定，而非再建任务影子库。
- 原 GOAL 的 M7 记录真实暴露了“工程机制就位，业务使用仍会中断”。`application/diagnostics/checks/usage-mileage.ts:9` 只提示建立本机台账，不能测量业务写回是否达标；本轮没有读取新的真实台账或复算 gbrain。历史资产样例也不能自动充当当前两周的新活动证据。

项目最有价值的现有基础，是对规范源、所有权、可见降级与恢复的重视。当前最需要的证据，是这些基础是否减少业务工作的重复说明、查找和交接成本。

## 外部官方证据：截至复审日能核验什么

以下是厂商或协议维护方的声明，不是横向效果评测。只采用发布时间不晚于 2026-10-18 的发布资料；滚动文档标明访问日期，不能据此回推历史上的首次可用时间。

### E1：工作界面正在整合，入口不再等于终端目录

Anthropic 于 **2026-09-16** 宣布将 Claude chat 与 Cowork 合并为一个自适应工作界面，同时支持对话、后台任务及本地/连接服务的工作。该公告还描述手机发起、桌面完成的衔接。它证明存在这种产品方向，不证明各套餐、平台或环境具备同等能力。

来源：[Cowork and Claude are now one](https://claude.com/blog/cowork-is-now-claude)。

**对 JSpace 的推论**：保留文件夹作为可靠本地入口；让愿景允许桌面、IDE 和移动入口引用同一份持久上下文。无需为此自建客户端。

### E2：跨应用上下文与持续执行正在成为工作代理的组成

Google 于 **2026-10-08** 在 Gemini at Work 发布 Gemini agent，描述跨 Gmail、Drive、Docs、Sheets、Slides 等应用执行工作，复用 memory、skills 与控制，以及从计划、调用工具到交付成果的流程。这是厂商宣布的产品能力，不代表所有用户或套餐在当日都已获得。

来源：[Welcome to Gemini at Work 2026: Introducing the Gemini agent](https://cloud.google.com/blog/products/ai-machine-learning/welcome-to-gemini-at-work-2026/)。

**对 JSpace 的推论**：资产与记忆应能为实际工作提供来源和结果链接；文件归档本身不足以定义完整工作中心。跨 SaaS 连接应按具体需求接入，不能从这篇公告推导出 JSpace 应复制所有连接器。

### E3：企业工作中心同时在建设语义上下文与 agent 管理

Microsoft 于 **2026-03-09** 在 Microsoft 365 Copilot Wave 3 公告中将 Work IQ 的工作关系上下文、可在应用内行动的 Copilot 与 Agent 365 管理放在同一产品方向中；其中明确区分上线、预览与未来可用时间。

来源：[Microsoft 365 Copilot Wave 3 / Frontier Suite 公告](https://blogs.microsoft.com/blog/2026/03/09/introducing-the-first-frontier-suite-built-on-intelligence-trust/)。

**对 JSpace 的推论**：可信来源、执行与可监督性需要一起考虑。但企业 IAM、组织级治理和合规控制并不是个人 JSpace 必须自建的范围。

### E4：现有执行产品已经提供后台工作与隔离环境

原 Codex app 官方路径在本轮访问时重定向到 ChatGPT desktop app 文档，描述并行项目、产物检查、跨工具与长任务。Scheduled tasks 文档区分网页任务与需要本地文件的桌面任务，后者可用项目目录或隔离 worktree，并要求电脑开机、应用运行。应使用重定向后的实际产品名称，不能照旧路径推断现行品牌和功能。

来源：[ChatGPT desktop app](https://learn.chatgpt.com/docs/app)、[Scheduled tasks](https://learn.chatgpt.com/docs/automations?surface=app)（访问日期均为 **2026-10-18**；分别从 `developers.openai.com/codex/app/` 与其 `automations/` 路径重定向）。

**对 JSpace 的推论**：执行和任务调度已有可复用产品，JSpace 不必竞做执行器；本地优先也不等于所有执行都必须发生在本地。任何远程接续仍需另行证明资料可用与授权充分。

### E5：长期任务需要持久进度与独立检查

Anthropic 于 **2026-03-24** 的工程文章讨论长任务中的上下文耗尽、自评不可靠与验收标准漂移，展示将规划、生成和评估分开的实验。它是具体场景的工程经验，不能证明每项工作都需要三种 agent。

来源：[Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)。

**对 JSpace 的推论**：跨会话接续与成果检查应成为目标；先使用可持久读取的交接材料与任务自身验收，不照搬其多 agent 架构。

### E6：协议解决连接，不替产品定义业务真相

MCP 的 **2025-11-25** 规范定义 host / client / server 的工具、资源、提示及连接责任；其架构没有替应用规定跨工具工作状态或统一记忆的业务语义。

来源：[MCP architecture](https://modelcontextprotocol.io/specification/2025-11-25/architecture)。

**对 JSpace 的推论**：可以复用开放协议接工具和资料；“支持 MCP”不能替代来源、权限、记忆纪律与交接验收。也无需仅为协议趋势新增适配层。

## 对“最终形态”的判断

上述证据共同支持的方向是：**持续的工作上下文、跨应用执行、可交付产物与人类监督正在结合。** 它们尚不能证明最终会收敛成单一超级应用、文件夹、聊天客户端或常驻 agent。

本文选择的可持续假设是：入口与执行者可以多样，用户长期积累的工作资料应能被不同入口理解和继续使用。这是架构取舍，不是已经被市场证明的唯一答案。

还存在相反的现实可能：单一厂商的原生记忆、连接器和产物体验足够好，使用户没有必要维护独立底座。对于长期只使用一个套件、几乎没有跨工具或本地资产需求的人，JSpace 未必划算。未来必须用维护成本和真实工作收益判断是否继续做，不能靠“可移植”这一标签自证必要。

## 旧 GOAL 的具体问题与修正

1. **价值描述被入口绑定。** “从一个总控文件夹启动任何 harness”描述了启动方式，不能覆盖其他工作入口。新目标写工作连续性，当前文件夹入口继续有效。
2. **机制齐全被当作终局。** 四大支柱缺少工作如何交接、成果如何验收的闭环。新目标补用户行为与可观察证据，明确目前只实现了部分能力。
3. **无常驻被绝对化。** 系统调度与第三方 harness 本身有运行环境要求。新目标保留“不引入 JSpace 自有常驻运行时”的当前选择，让是否新增机制由真实需求裁决。
4. **“不做自主代理”范围过宽。** 容易把有边界、可监督的委托执行也排除。新目标区分不自研执行/编排平台与可以复用现有 harness；授权、责任、验收仍明确。
5. **记忆命中被赋予过强意义。** 最近项目摘要不等于本次任务的完整上下文，记忆页不等于最新权威版本。新目标强调规范源、核对和失效管理。
6. **指标偏向工具自证。** 写回数量与调度成功有工程价值，不能单独证明业务收益。新目标保留 M7 原标准，增加真实接续、正确取件、产物与维护成本的观察。
7. **愿景与历史混在一起。** 原稿约 34.6 KB，含历史统计与已修复缺陷。原文完整保存到历史快照，现行目标只保留方向、有效协议、开放证据与演进闸门。

## 应保留的设计

- 用户拥有的文本与普通文件、本机绑定、分层同步。
- gbrain 与现有 harness 分工；资产本体和记忆指针分工。
- 显式写回、来源标签、状态卡与项目执行细节分离。
- journal / pending / incident / 升级恢复，以及能力分级与不虚报自动化。
- 真实使用优先、M7 关闭前不扩大记忆分类学、只由实际问题触发工程 backlog。

目标优化没有要求本轮迁移用户资产、改真实工作台、扩大权限或部署服务。

## 最小的下一步

先继续 M7。把一次真实工作的目标、规范来源、状态、产物和下一步指针留在已有位置，观察下次会话能否接手。再在两个非 JSpace 业务项目中采集五次自然交接（至少两次换 harness），记录重复解释、错版本、来源缺失和人工修正。

候选实验的首轮门槛为五次中至少四次能开始正确的下一步，关键事实、版本与权限不能发生未被识别的错误；这是假设检验的起点，不是当前成绩。样本少，只能决定是否值得继续试，不能外推出普遍收益。

若缺口来自文档遗漏，修文档；来自产物无法验收，补该任务的检查；来自入口无法访问规范资料，再做那个入口的最小适配。只有反复出现且既有载体无法承担的需求，才值得升级为新契约。
